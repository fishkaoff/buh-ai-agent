# onec-contracts — договоры контрагентов 1С

## Когда использовать

- Найти договор контрагента для документа (счёт, реализация, платёж).
- Определить «последний подходящий договор».
- Создать новый договор.

Метаданные `Catalog_ДоговорыКонтрагентов` — Skill `onec-metadata` / `docs/onec-metadata-map.md`. Подчинённый справочник: владелец — контрагент (поле **`Owner_Key`**, не `Контрагент_Key`).

## Поиск договоров контрагента

```js
GET Catalog_ДоговорыКонтрагентов?$format=json&$top=200
// локально: d.Owner_Key === <Ref_Key контрагента> && !d.DeletionMark
```

(серверный фильтр по `Owner_Key eq guid'...'` тоже работает). Выборка договоров мала даже в больших базах.

Ключевые реквизиты (проверено): `Description`, `Номер`, `Дата`, `ВидДоговора`, `Организация_Key`, `ВалютаВзаиморасчетов_Key`, `СрокОплаты`/`УстановленСрокОплаты`, `СпособЗаполненияСтавкиНДС`, `СтавкаНДС`, `СуммаВключаетНДС`, `ДоговорЗакрыт`.

## Выбор договора

1. Фильтр: владелец = контрагент документа; `ДоговорЗакрыт=false`.
2. **Вид договора** (`ВидДоговора`) соответствует операции: продажа — `СПокупателем`, закупка — `СПоставщиком` (полный список перечисления — `docs/onec-metadata-map.md`).
3. Несколько подходящих — «последний» = максимум пары (`Дата`, `Номер`); сообщите пользователю выбранный договор (наименование, номер, дата).
4. Нет подходящего — предложите создать (ниже), вид договора согласуйте с пользователем.

## Правила нумерации (исследовано, важно)

Факты этой конфигурации (база ai_agent, 10.11.2026):

- `Code` 1С нумерует сама: `00-000001`, `00-000002`, … — сквозная, надёжная (проверено на созданиях).
- `Номер` — обычный строковый реквизит. **1С через OData его не заполняет** — останется пустым, если не задать.
- В существующих данных `Номер` = 1, 2, 3 — сквозная последовательность по всем контрагентам; `Description` построен как «`Номер` от `ДД.ММ.ГГГГ`». Это след прошлых созданий, а не механизм 1С.

Правила безопасного назначения номера (по приоритету):

1. Пользователь назвал номер → использовать как есть.
2. Иначе кандидат = max(числовых `Номер` всех договоров) + 1 — соответствует практике базы. Проверить занятость.
3. Надёжно определить не удалось (нечисловые/смешанные номера, конфликт) → спросить пользователя или оставить «б/н».
4. `Description` — по образцу данных: «`Номер` от `ДД.ММ.ГГГГ`».

Не рассчитывайте на автонумерацию `Номер` от 1С через OData — её нет. Автонумерация у `Code` и у номеров документов.

## Создание договора

POST `Catalog_ДоговорыКонтрагентов?$format=json` — проверенный минимум:

```json
{
  "Description": "4 от 10.11.2026",
  "Номер": "4",
  "Дата": "2026-11-10T00:00:00",
  "Owner_Key": "<GUID контрагента>",
  "Организация_Key": "<GUID организации>",
  "ВидДоговора": "СПокупателем",
  "ВалютаВзаиморасчетов_Key": "<GUID руб. (Code 643)>"
}
```

Ответ 201 → `Ref_Key` и `Code`. Порядок: предпросмотр payload → согласие → POST → перечитать (владелец, вид, организация, валюта, номер). Проверить отсутствие у контрагента договора с тем же номером.

- `ВидДоговора` обязателен; пользователь не назвал вид — спросите (контрагент может быть и покупателем, и поставщиком).
- Организация — основная/единственная базы, если пользователь не указал иную.

## Вспомогательный скрипт

`scripts/next_contract_number.js [Ref_Key контрагента]` — вычисляет кандидата следующего номера по правилам выше и проверяет занятость (ничего не записывает).

## Ограничения

- Не редактируйте существующие договоры (номер/вид/организация) без явного разрешения — на них ссылаются документы.
- Закрытые (`ДоговорЗакрыт`) не использовать для новых документов.
- «Прочее» — только когда операция не продажная и не закупочная.
