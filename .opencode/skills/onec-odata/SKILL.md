# onec-odata — прямой доступ к 1С по OData (без MCP)

## Когда использовать

- Любое чтение/создание/изменение объектов 1С по HTTP.
- Разбор ошибок и особенностей OData-запросов к 1С.

Skill самодостаточен: нужны только сеть и `config/onec-config.json`. Никаких MCP-зависимостей.

## Подключение

Креды, URL и список баз — в `config/onec-config.json` (корень проекта; переопределяются env: `ODATA_BASE_URL`, `ODATA_USERNAME`, `ODATA_PASSWORD`, `ONEC_DATABASE`, `ONEC_CONFIG`). Общий HTTP-клиент без зависимостей (Node ≥ 18): `config/onec/odata-client.js`.

```js
const { client, rows, obj, parseError, docDate } = require("<корень проекта>/config/onec/odata-client.js");
const c = client();                    // база по умолчанию; client("ai_agent") — явно
const r = await c.req("GET", c.BASE + "Catalog_Контрагенты?$format=json&$top=10");
const list = rows(r.body);             // массив value
```

В не-Node средах — любой HTTP-клиент: Basic-авторизация (`base64(login:password)` в заголовке `Authorization`), к каждому URL добавляется `$format=json`.

## Структура URL

```
{BASE}EntitySet?$format=json&$filter=...&$select=...&$orderby=...&$top=...&$skip=...
{BASE}EntitySet(guid'REF')?$format=json                          # один объект
{BASE}EntitySet_ИмяТабличнойЧасти?$filter=Ref_Key eq guid'REF'   # строки табличной части
```

- `{BASE}` заканчивается на `/` (например `http://192.168.3.2/InfoBase2/odata/standard.odata/`); база зашита в путь.
- **Всегда `$format=json`** — иначе ответ XML.
- Имена EntitySet технические, с кириллицей: `Catalog_Контрагенты`, `Document_РеализацияТоваровУслуг` (как найти — Skill `onec-metadata`).

## Проверенные запросы (OData 3.0 1С)

| Задача | Работает | НЕ работает |
|---|---|---|
| Фильтр по подстроке | `$filter=substringof('текст', Description)` | `contains(...)` → 400 |
| Регистр | 1С сравнивает строки **без учёта регистра** | `tolower(...)` → 400 |
| Равенство | `ИНН eq '7701234567'`, `ВидДоговора eq 'СПокупателем'` | — |
| Логика | `and`, `or`, скобки; GUID: `Ref_Key eq guid'35a7...'` | — |
| Сортировка/лимиты | `$orderby=Date desc&$top=50&$skip=100` | — |
| Поля | `$select=Ref_Key,Number,СуммаДокумента` | — |
| По ключу | `EntitySet(guid'...')` | key-lookup табличной части `..._Товары(guid'...')` → 404 |
| Табличные части | `..._Товары?$filter=Ref_Key eq guid'...'` (у строк `Ref_Key` = ключу документа, различаются `LineNumber`) | `$expand=Товары` → 501 |

Фильтр URL-кодируйте (`encodeURIComponent`): кириллица и пробелы обязательны.

## Чтение, создание, изменение

- **Чтение списка**: GET → `{ "value": [...] }`; пагинация `$top/$skip` или фильтрация.
- **Чтение по ключу**: GET `EntitySet(guid'...')?$format=json` → объект.
- **Создание**: POST `EntitySet?$format=json` с JSON-телом. Успех — **201**, в ответе объект с присвоенными `Ref_Key`, `Number`/`Code` (1С нумерует сама; **не отправляйте `Number` документа**). Автозаполнение реквизитов из форм 1С работает не всё — перечитывайте и дозаполняйте PATCH-ом.
- **Изменение**: PATCH `EntitySet(guid'...')?$format=json` только с изменяемыми полями; успех — 200/204; после — перечитайте и сверьте.
- **Табличная часть** — массивом в теле POST/PATCH (отдельные POST строк не нужны):
  ```json
  { "Товары": [ { "LineNumber": 1, "Номенклатура": "GUID", "Номенклатура_Type": "StandardODATA.Catalog_Номенклатура",
      "Количество": 40, "Цена": 200, "Сумма": 8000 } ] }
  ```
- **Составные ссылки**: `Поле` (GUID) + `Поле_Type` (`StandardODATA.Catalog_Имя`).
- **Проведение**: PATCH `{ "Posted": true }` по ключу (отмена — `false`). Отдельная операция, не объединять с созданием.

## Типы данных 1С в OData

| Тип | Представление |
|---|---|
| Ссылка | `Поле_Key: Edm.Guid` |
| Составная ссылка | `Поле` (GUID) + `Поле_Type` |
| Дата/время | `Edm.DateTime`; отправляйте `"YYYY-MM-DDT00:00:00"` без `Z` — суффикс `Z`/миллисекунды смещают значение |
| Число | `Edm.Double` / `Edm.Int64` |
| Перечисление | `Edm.String` со значением члена (списки — из `$metadata`, Skill `onec-metadata`) |
| Табличная часть | `Collection(...RowType)` в шапке; отдельный EntitySet `..._Имя` для чтения |
| Версия | `DataVersion: Edm.String` |

## Безопасная запись (вместо MCP dry-run/confirm)

1. Подготовить payload, показать пользователю.
2. Получить явное согласие.
3. Выполнить POST/PATCH.
4. Перечитать объект, сверить (Skill `onec-validation`).
5. Повторные вызовы — только после антидубликат-поиска (OData идемпотентности нет).

## Обработка ошибок

- Ошибки 1С: `{"odata.error":{"code":"N","message":{"value":"..."}}}` — разбор `parseError(status, body)`, каталог — Skill `onec-error-handling`.
- 401 — креды; 404(HTML) — путь/порт; 400 — неверный фильтр/поле; 501 — неподдержанная опция; 500 — бизнес-логика 1С (причина часто расплывчата — упрощайте payload и повторяйте диагностику).
- Соединение закрыто/таймаут — 1С обрабатывает запросы учётки по очереди: один повтор, без параллельных вызовов.

## Ограничения (проверено)

- Печатные формы и PDF через OData не получить (Skill `onec-print-forms`).
- Физическое удаление недоступно (только PATCH `DeletionMark`).
- Нет транзакций; дубликаты исключаются предварительным поиском.
- MCP-сервер `1c-odata` (если установлен в среде) дублирует эти операции удобными инструментами — его возможности описаны в `docs/onec-capabilities.md`, но все Skills работают и без него.
